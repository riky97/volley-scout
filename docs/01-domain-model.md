# Volley Scout — Domain Model & Rules Specification

> Phase 1 / P1.2. Refines [00-product-plan.md](00-product-plan.md) (assumptions A1..A9). Nothing here
> contradicts the plan; where the plan was a sketch, this document is the binding contract.
> All identifiers are English. Italian appears only in UI-label columns.
> Target: `tsconfig` `strict: true`, `noUncheckedIndexedAccess: true`, `exactOptionalPropertyTypes: true`, **no `any`**.

**Module placement** — every type and function below lives under `src/domain/`:

```
src/domain/
  entities/        team.ts player.ts match.ts set.ts event.ts settings.ts
  rules/           outcome.ts scoring.ts serving.ts rotation.ts lifecycle.ts undo.ts
  projection/      snapshot.ts        (fold of the event log)
  statistics/      see 02-statistics.md
```

Rules are **pure**: no React, no IO, no `Date.now()` inside them (timestamps are passed in by the
application layer), no mutation of inputs. Every function returns new values.

## 1. Primitive types and conventions

```ts
/** UUID v4, generated by the application layer via crypto.randomUUID(). */
export type Id = string;

/** ISO-8601 with milliseconds and timezone offset, e.g. "2026-09-22T19:04:11.482+02:00". */
export type IsoTimestamp = string;

/** Calendar date, "YYYY-MM-DD". */
export type IsoDate = string;

/** The only two parties the app knows about (A1). */
export type TeamSide = 'us' | 'them';

/** Current schema of every persisted root document. */
export const SCHEMA_VERSION = 1 as const;
export type SchemaVersion = typeof SCHEMA_VERSION;
```

Rules that every persisted root obeys:

- `schemaVersion: 1` is a **literal** field, always present, always first in the serialised object.
- Persisted roots are exactly three: `Match`, `RosterTemplate`, `AppSettings`.
  `Team`, `Player`, `SetState`, `ScoutEvent`, `Lineup` are embedded, never stored standalone.
- `MatchSnapshot` and all statistics are **derived**, never persisted (they are recomputed on load).

### 2.3 Player

```ts
export interface Player {
  readonly id: Id;
  /** 0..99 inclusive. Uniqueness inside a roster is validated, not enforced by the type. */
  readonly shirtNumber: number;
  /** Full name as typed, 1..60 chars, trimmed, may contain spaces. */
  readonly name: string;
```

Violations are tolerated on read and surfaced as "unknown player" (edge case E19).

### 2.7 Skill and EventOutcome

```ts
export type Skill = 'serve' | 'reception' | 'attack' | 'block' | 'dig' | 'set';

export type EventOutcome = 'point' | 'positive' | 'neutral' | 'negative' | 'error';

export const SKILLS: readonly Skill[] = ['serve', 'reception', 'attack', 'block', 'dig', 'set'] as const;
export const OUTCOMES: readonly EventOutcome[] =
  ['point', 'positive', 'neutral', 'negative', 'error'] as const;
```

Allowed combinations (§6 of the plan, made exhaustive and machine-readable):

```ts
export const ALLOWED_OUTCOMES: Readonly<Record<Skill, readonly EventOutcome[]>> = {
  serve:     ['point', 'positive', 'neutral', 'negative', 'error'],
  reception: ['positive', 'neutral', 'negative', 'error'],
  attack:    ['point', 'positive', 'neutral', 'negative', 'error'],
  block:     ['point', 'positive', 'neutral', 'error'],
  dig:       ['positive', 'neutral', 'negative', 'error'],
  set:       ['positive', 'neutral', 'negative', 'error'],
} as const;

export function isAllowedOutcome(skill: Skill, outcome: EventOutcome): boolean {
  return ALLOWED_OUTCOMES[skill].includes(outcome);
}
```

A combination outside this table is **rejected at event creation** (the action pad never offers it)
and, if found on load, the event is flagged invalid (edge case E20).

### 2.8 CourtPosition and Lineup

```ts
/** Rotational positions, volleyball numbering. P1 = right back and serving position. */
export type CourtPosition = 'P1' | 'P2' | 'P3' | 'P4' | 'P5' | 'P6';

export const COURT_POSITIONS: readonly CourtPosition[] =
  ['P1', 'P2', 'P3', 'P4', 'P5', 'P6'] as const;

/**
 * Six player ids in *initial* court order: index 0 is the player who started the set in P1,
 * index 1 the one who started in P2, ... index 5 the one who started in P6.
 * The array itself NEVER rotates. Rotation is expressed by SetState.rotationOffset.
 * Substitutions replace the id **in place**, at the slot of the outgoing player.
 */
export type Lineup = readonly [Id, Id, Id, Id, Id, Id];
```

**Invariant L1** — the six ids are distinct, all present in `Match.roster`, all `isAvailable`.
**Invariant L2** — a set cannot start without a complete `Lineup`.

### 2.10 ScoutEvent (discriminated union on `type`)

Common shape, shared by every variant:

```ts
interface ScoutEventBase {
  readonly id: Id;
  readonly timestamp: IsoTimestamp;
  /** 0-based set this event belongs to. */
  readonly setIndex: number;
  /**
   * Monotonic position in the match-wide event log, assigned on append (0, 1, 2, ...).
   * Recomputed densely after a delete. Used for stable ordering and for undo.
   */
  readonly sequence: number;
}

/** Score pair, always "our points first". */
export interface Score {
  readonly us: number;
  readonly them: number;
}
```

Rally-affecting events additionally carry the score transition. This makes the log **self-describing**:
a reader never needs to replay the whole match to know the score at a given row, and a mismatch
between stored and recomputed values is a detectable corruption (edge case E21).

```ts
interface RallyAffecting {
  readonly scoreBefore: Score;
  readonly scoreAfter: Score;
  /** Which side got the point; null only for non-terminal rally events. */
  readonly pointTo: TeamSide | null;
  /** Who was serving when the rally started. */
  readonly servingBefore: TeamSide;
  /** Who serves the next rally. */
  readonly servingAfter: TeamSide;
  /** Our rotationOffset before / after the rally. */
  readonly rotationBefore: number;
  readonly rotationAfter: number;
}
```

The seven variants:

```ts
export interface RallyEvent extends ScoutEventBase, RallyAffecting {
  readonly type: 'rally';
  /** Acting player of OUR team (A1). Must exist in the roster. */
  readonly playerId: Id;
  readonly skill: Skill;
  readonly outcome: EventOutcome;
  /** true when this event ended the rally (see isTerminalOutcome). Mirrors pointTo !== null. */
  readonly isTerminal: boolean;
  /** Free operator annotation on the single action, 0..200 chars. */
  readonly comment: string;
}

/** Opponent winner or opponent action we do not attribute to one of our players (A1). */
export interface OpponentPointEvent extends ScoutEventBase, RallyAffecting {
  readonly type: 'opponent_point';
  readonly pointTo: 'them';
  readonly comment: string;
}

export interface TimeoutEvent extends ScoutEventBase {
  readonly type: 'timeout';
  readonly team: TeamSide;
  /** Score when the timeout was called, for the report. */
  readonly atScore: Score;
}

export interface SubstitutionEvent extends ScoutEventBase {
  readonly type: 'substitution';
  readonly playerOutId: Id;
  readonly playerInId: Id;
  /** Lineup slot (0..5) that changed, i.e. index of playerOutId in the lineup array. */
  readonly lineupSlot: number;
  readonly atScore: Score;
}

export interface SetStartEvent extends ScoutEventBase {
  readonly type: 'set_start';
  readonly lineup: Lineup;
  readonly servingTeam: TeamSide;
  /** Points needed to win this set (pointsToWinSet or pointsToWinTieBreak), frozen at start. */
  readonly target: number;
}

export interface SetEndEvent extends ScoutEventBase {
  readonly type: 'set_end';
  readonly winner: TeamSide;
  readonly finalScore: Score;
  /** Sets won by each side **after** this set closed. */
  readonly setsAfter: Readonly<Record<TeamSide, number>>;
  /** true when this set ended the match. */
  readonly endsMatch: boolean;
}

export interface NoteEvent extends ScoutEventBase {
  readonly type: 'note';
  readonly text: string;               // 1..500 chars
  readonly atScore: Score;
}

export type ScoutEvent =
  | RallyEvent
  | OpponentPointEvent
  | TimeoutEvent
  | SubstitutionEvent
  | SetStartEvent
  | SetEndEvent
  | NoteEvent;

export type ScoutEventType = ScoutEvent['type'];
```

Narrowing helper used everywhere instead of `as`:

```ts
export function isRallyAffecting(e: ScoutEvent): e is RallyEvent | OpponentPointEvent {
  return e.type === 'rally' || e.type === 'opponent_point';
}
```

**Ordering** — `Match.events` is a single append-only array for the whole match, sorted by
`sequence`, never re-sorted by `timestamp` (the operator's clock may jitter).

## 3. Rules specification

All functions below are pure and total: every input combination has a defined result.

### 3.1 Terminal outcomes — `isTerminalOutcome`

```ts
export interface TerminalResult {
  readonly isTerminal: boolean;
  /** null when the rally continues. */
  readonly pointTo: TeamSide | null;
}

export function isTerminalOutcome(skill: Skill, outcome: EventOutcome): TerminalResult;
```

Behaviour — exhaustive, **outcome-driven and skill-independent**:

| outcome | result | reason |
|---|---|---|
| `point` | `{ isTerminal: true, pointTo: 'us' }` | ace, kill, block point |
| `error` | `{ isTerminal: true, pointTo: 'them' }` | our error of any skill |
| `positive` | `{ isTerminal: false, pointTo: null }` | rally continues |
| `neutral` | `{ isTerminal: false, pointTo: null }` | rally continues |
| `negative` | `{ isTerminal: false, pointTo: null }` | rally continues |

Full skill × outcome matrix (`—` = combination not offered, see `ALLOWED_OUTCOMES`; calling the
function with it still returns the outcome-driven value, it simply never happens in practice):

| skill \ outcome | point | positive | neutral | negative | error |
|---|---|---|---|---|---|
| serve | us | cont. | cont. | cont. | them |
| reception | — | cont. | cont. | cont. | them |
| attack | us | cont. | cont. | cont. | them |
| block | us | cont. | cont. | — | them |
| dig | — | cont. | cont. | cont. | them |
| set | — | cont. | cont. | cont. | them |

Rationale (A2): exactly one terminal event per rally. `attack` + `negative` means "blocked or dug by
the opponent, rally continues"; if the opponent then converts, the operator records a separate
`opponent_point` event. An `OpponentPointEvent` is always terminal with `pointTo: 'them'`.

### 3.2 Scoring

Rally point system: **every** rally awards exactly one point, to `pointTo`.

```ts
export function applyPoint(score: Score, pointTo: TeamSide): Score {
  return pointTo === 'us'
    ? { us: score.us + 1, them: score.them }
    : { us: score.us, them: score.them + 1 };
}

/**
 * True when `ourPoints` wins the set against `theirPoints`.
 * Always evaluated from one side's perspective; call twice to know who won.
 */
export function isSetWon(
  ourPoints: number,
  theirPoints: number,
  target: number,
  winByTwo: boolean,
): boolean {
  if (ourPoints < target) return false;
  if (!winByTwo) return ourPoints > theirPoints || ourPoints >= target;
  return ourPoints - theirPoints >= 2;
}
```

Exhaustive behaviour with `target = 25, winByTwo = true`:

| ourPoints | theirPoints | result | note |
|---|---|---|---|
| 24 | 20 | false | below target |
| 25 | 20 | true | normal |
| 25 | 23 | true | margin 2 |
| 25 | 24 | false | deuce, play on |
| 26 | 24 | true | |
| 26 | 25 | false | |
| 30 | 28 | true | **no cap** (A6): deuce continues indefinitely |
| 41 | 39 | true | |

With `winByTwo = false`: `25-24 → true` (first to reach target wins). This mode is not exposed in
the MVP UI; it exists for tests and for exotic youth formats.

**Target selection**:

```ts
export function targetForSet(settings: MatchSettings, setIndex: number): number {
  return setIndex === settings.bestOf - 1
    ? settings.pointsToWinTieBreak
    : settings.pointsToWinSet;
}
```

**Match end**:

```ts
export function setsNeededToWin(bestOf: BestOf): number {
  return bestOf === 3 ? 2 : 3;                    // Math.floor(bestOf / 2) + 1
}

export function isMatchWon(setsWon: number, bestOf: BestOf): boolean {
  return setsWon >= setsNeededToWin(bestOf);
}
```

| bestOf | setsWon | isMatchWon |
|---|---|---|
| 3 | 0,1 | false |
| 3 | 2,3 | true |
| 5 | 0,1,2 | false |
| 5 | 3,4,5 | true |

A match can never exceed `bestOf` sets: after the `bestOf - 1` index set, one side necessarily has
`setsNeededToWin`.

### 3.3 Serving — side-out logic

```ts
/** Who serves the next rally. */
export function nextServingTeam(servingBefore: TeamSide, pointTo: TeamSide): TeamSide {
  return pointTo;
}

/** True when the point caused a side-out (the receiving team won the rally). */
export function isSideOut(servingBefore: TeamSide, pointTo: TeamSide): boolean {
  return servingBefore !== pointTo;
}
```

Exhaustive:

| servingBefore | pointTo | next server | side-out |
|---|---|---|---|
| us | us | us | no |
| us | them | them | yes |
| them | them | them | no |
| them | us | us | yes |

The serving team is a property of `SetState`, not of the event: the rule "the winner of the rally
serves next" is universal in the rally point system.

### 3.4 Rotation

**Mapping rule** — `rotationOffset` counts clockwise rotations performed since the set started.
The player standing in position `Pn` (n = 1..6) is:

```ts
export function playerAtPosition(
  lineup: Lineup,
  rotationOffset: number,
  position: CourtPosition,
): Id {
  const n = COURT_POSITIONS.indexOf(position);        // 0 for P1 .. 5 for P6
  return lineup[(n + rotationOffset) % 6] as Id;
}

export function courtOf(lineup: Lineup, rotationOffset: number): readonly PositionedPlayer[] {
  return COURT_POSITIONS.map((position, n) => ({
    position,
    playerId: lineup[(n + rotationOffset) % 6] as Id,
  }));
}
```

Read it as: *offset 1 means everybody moved one step clockwise, so the player who started in P2 is
now in P1.* Clockwise on court is `P2 → P1 → P6 → P5 → P4 → P3 → P2`, which is exactly "the P2 player
takes over P1", i.e. `+1` on the array index for the same position label.

**When to rotate**:

```ts
export function shouldRotate(servingBefore: TeamSide, pointTo: TeamSide): boolean {
  return isSideOut(servingBefore, pointTo);          // the receiving team that wins rotates
}

export function nextRotationOffset(
  currentOffset: number,
  servingBefore: TeamSide,
  pointTo: TeamSide,
): number {
  // We only track OUR rotation (A1): we rotate when WE were receiving and WE won the rally.
  const weRotate = servingBefore === 'them' && pointTo === 'us';
  return weRotate ? (currentOffset + 1) % 6 : currentOffset;
}
```

| our state before | pointTo | our rotationOffset |
|---|---|---|
| we serve | us | unchanged |
| we serve | them | unchanged (*they* rotate — not modelled, A1) |
| they serve | us | `(offset + 1) % 6` |
| they serve | them | unchanged |

**Current server**:

```ts
export function currentServerId(set: SetState): Id | null {
  if (set.servingTeam !== 'us' || set.lineup === null) return null;
  return playerAtPosition(set.lineup, set.rotationOffset, 'P1');
}
```

When `servingTeam === 'them'` the UI shows the opponent name as server; there is no opponent player
model (A1). The server is recomputed from the offset **after** rotation, i.e. a side-out immediately
promotes the incoming P1 to server.

**Libero** (A4): the libero is **not** removed from or inserted into the lineup automatically. If the
operator put the libero in the lineup, the libero can end up in P1 and be shown as server; the UI
shows a non-blocking warning "Il libero non può battere" and lets the operator proceed.

### 3.5 Set and match lifecycle

```ts
export interface StartSetInput {
  readonly match: Match;
  readonly lineup: Lineup;
  readonly timestamp: IsoTimestamp;
}
export function startSet(input: StartSetInput): Match;        // appends a SetStartEvent
```

Behaviour:

1. Allowed only when `match.status` is `'setup'` (first set) or `'live'` with the previous set
   `'finished'` and the match not yet won. Otherwise it throws `DomainError('SET_ALREADY_LIVE')`.
2. `setIndex = match.sets.length`.
3. `target = targetForSet(match.settings, setIndex)`.
4. **Serving team for the set** — alternating first server:
   ```ts
   export function firstServerOfSet(settings: MatchSettings, setIndex: number): TeamSide {
     const flip = setIndex % 2 === 1;
     return flip
       ? (settings.startingServer === 'us' ? 'them' : 'us')
       : settings.startingServer;
   }
   ```
   *Tie-break exception*: in the real rules the deciding set's first server is decided by a fresh
   toss. The MVP pre-fills the alternating value and the set-start dialog lets the operator
   **override** it with a radio ("Chi batte?"). The chosen value is stored in `SetStartEvent.servingTeam`,
   which always wins over `firstServerOfSet`.
5. **Side** — sides alternate each set, `startingSide` flipped when `setIndex % 2 === 1`. Purely
   cosmetic (which half of the court widget we are drawn on). The mid-tie-break switch at 8 points is
   **not modelled** in the MVP.
6. `rotationOffset` starts at `0`, `ourPoints`/`theirPoints` at `0`, `timeoutsUsed` at `{us:0,them:0}`,
   `substitutionsUsed` at `0`, `status: 'live'`, `startedAt = timestamp`.
7. `match.status` becomes `'live'`.

**Rally application** — the single entry point for every rally-affecting event:

```ts
export interface AppendRallyInput {
  readonly match: Match;
  readonly event:
    | Omit<RallyEvent, keyof RallyAffecting | 'id' | 'sequence' | 'isTerminal'>
    | Omit<OpponentPointEvent, keyof RallyAffecting | 'id' | 'sequence'>;
  readonly id: Id;
  readonly timestamp: IsoTimestamp;
}
export function appendRallyEvent(input: AppendRallyInput): Match;
```

Order of operations, strictly:

1. Resolve the live set; if there is none → `DomainError('NO_LIVE_SET')`.
2. `scoreBefore = { us: set.ourPoints, them: set.theirPoints }`, `servingBefore = set.servingTeam`,
   `rotationBefore = set.rotationOffset`.
3. `{ isTerminal, pointTo } = isTerminalOutcome(skill, outcome)` (or `true/'them'` for `opponent_point`).
4. If **not** terminal: `scoreAfter = scoreBefore`, `pointTo = null`, `servingAfter = servingBefore`,
   `rotationAfter = rotationBefore`. The set is untouched. Append and stop.
5. If terminal: `scoreAfter = applyPoint(scoreBefore, pointTo)`;
   `rotationAfter = nextRotationOffset(rotationBefore, servingBefore, pointTo)`;
   `servingAfter = nextServingTeam(servingBefore, pointTo)`.
6. Append the event, update the `SetState`.
7. Evaluate set end (below). **Never** auto-append `set_end` — see next paragraph.

**Set end** — the domain *detects* it, the application *confirms* it:

```ts
export function evaluateSetEnd(set: SetState, settings: MatchSettings): TeamSide | null {
  const target = targetForSet(settings, set.index);
  if (isSetWon(set.ourPoints, set.theirPoints, target, settings.winByTwo)) return 'us';
  if (isSetWon(set.theirPoints, set.ourPoints, target, settings.winByTwo)) return 'them';
  return null;
}

export function endSet(match: Match, id: Id, timestamp: IsoTimestamp): Match;
```

`evaluateSetEnd` returning non-null makes the UI open the set-end dialog; the operator confirms and
`endSet` appends the `SetEndEvent`, sets `status: 'finished'`, `winner`, `endedAt`. Keeping it manual
is what makes "undo across a set boundary" (E3) safe: nothing structural happens behind the operator.

`endSet` computes `setsAfter` by counting finished sets per winner, and
`endsMatch = isMatchWon(setsAfter[winner], settings.bestOf)`.

**Match end**:

```ts
export function endMatch(match: Match, timestamp: IsoTimestamp): Match;   // status -> 'finished'
export function abandonMatch(match: Match, timestamp: IsoTimestamp): Match; // status -> 'abandoned'
```

`endMatch` requires the last `SetEndEvent` to have `endsMatch: true`. It sets `closedAt` and makes the
match read-only: every append/edit/delete on a `finished` or `abandoned` match throws
`DomainError('MATCH_CLOSED')`. Re-opening is possible only via an explicit "Riapri partita" action
that flips the status back to `'live'` and is confirmed by the operator.

### 3.6 Non-rally events

- `timeout` — appended only while a set is `'live'`; increments `timeoutsUsed[team]`. When the counter
  exceeds `settings.timeoutsPerSet` the application shows a warning and still appends (A5).
- `substitution` — appended only while a set is `'live'`. Requires `playerInId` available, not already
  on court, and `playerOutId` currently on court. It **replaces the id in the lineup array at
  `lineupSlot`**, so `rotationOffset` and every position mapping stay valid.
  `substitutionsUsed += 1`; over-limit = warning, not a block (A5).
- `set_start` / `set_end` — described above.
- `note` — appendable at any time while the match is `'live'` (including between sets); carries
  `atScore` for the report. Never affects state.

### 3.7 Undo semantics

```ts
/** Which event types can be undone by the undo button. */
export function isUndoable(event: ScoutEvent): boolean {
  return event.type !== 'set_start';
}

export function undoLastEvent(match: Match): Match;
```

Contract:

1. Undo pops the **last event by `sequence`**, nothing else. There is no "undo a chosen event" — that
   is the event log's *delete*, see §3.8.
2. After popping, the match state is **recomputed from scratch** by folding the remaining events
   (`rebuildFromEvents`). It is never patched incrementally. This is what guarantees that score,
   serving team, rotation offset, lineup, timeout and substitution counters, set status, set list and
   match status all return to exactly the values they had before the undone event.
3. Concretely, popping restores:
   - `rally` / `opponent_point` → `ourPoints`, `theirPoints`, `servingTeam`, `rotationOffset`
     (from the event's `*Before` fields, verified against the fold);
   - `timeout` → `timeoutsUsed[team] - 1`;
   - `substitution` → the lineup slot returns to `playerOutId`, `substitutionsUsed - 1`;
   - `set_end` → the set returns to `status: 'live'`, `winner: null`, `endedAt: null`, and the match
     returns to `status: 'live'` if it had been closed;
   - `note` → nothing beyond removing the row.
4. `set_start` is **not** undoable by the undo button (it would orphan the whole set). The operator
   removes a set via "Annulla set" in the set menu, which deletes the `set_start` **and all events of
   that set** after an explicit confirmation.
5. Undo is unavailable (`canUndo: false`) when: the log is empty, the only remaining event is
   `set_start`, or `match.status` is `'finished'` / `'abandoned'` (the match must be re-opened first).
6. Undo depth is unlimited within the current match — it is simply repeated popping.
7. **Redo** is a single-slot buffer held in the application store (not in the domain, not persisted):
   the last undone event can be re-appended as long as no new event was appended and the app was not
   restarted.

### 3.8 Edit and delete of an arbitrary event

```ts
export function deleteEvent(match: Match, eventId: Id): Match;
export function editEvent(
  match: Match,
  eventId: Id,
  patch: { readonly playerId?: Id; readonly skill?: Skill; readonly outcome?: EventOutcome; readonly comment?: string },
): Match;
export function rebuildFromEvents(
  header: Pick<Match, 'schemaVersion' | 'id' | 'status' | 'createdAt' | 'info' | 'settings' | 'roster'>,
  events: readonly ScoutEvent[],
): Match;
```

Both operations do the same three steps: apply the change to the event array, re-densify `sequence`,
then `rebuildFromEvents`. **All downstream events are recomputed**, so their `scoreBefore/After`,
`serving*`, `rotation*` fields change accordingly — which may flip a set winner or even the match
result. The UI warns about this with the number of affected subsequent events before confirming.
Deleting a `set_start` deletes the whole set (same rule as §3.7.4). Deleting a `set_end` reopens the set.

## 4. Edge cases

| # | Case | Expected behaviour |
|---|---|---|
| E1 | Score reaches 24-24 in a normal set | No winner. `isSetWon` false both ways. Play continues; the UI shows "Ai vantaggi". |
| E2 | Score 25-24 | Not a set win (margin 1). Nothing structural happens. |
| E3 | Score 26-24 | `evaluateSetEnd` returns `'us'`; the set-end dialog opens; the set closes only on confirm. |
| E4 | Deuce runs to 35-33 | Allowed, no cap (A6). Score fields are plain numbers; the scoreboard layout must fit 2 digits without reflow. |
| E5 | Set point in the tie-break (14-13, target 15) | Same rule with `target = pointsToWinTieBreak`. UI badge "Set point" when a single point would satisfy `isSetWon` for either side. |
| E6 | Tie-break reached but `bestOf` is 3 and it is set index 2 | `targetForSet` returns `pointsToWinTieBreak` (15). Only index `bestOf - 1` is a tie-break. |
| E7 | Undo immediately after `set_end` | The `set_end` is popped; the set returns to `'live'` with its final score intact (e.g. 25-23); the match leaves `'finished'` if it had been closed. The next event can be appended normally. |
| E8 | Undo after `set_start` of set 2, i.e. undoing across a set boundary | `set_start` is not undoable (§3.7.4). The undo button is disabled and labelled "Niente da annullare"; the operator must use "Annulla set", which removes set 2 entirely and returns to the set-2 setup screen with set 1 still finished. |
| E9 | Undo when the log is empty | `canUndo: false`; `undoLastEvent` is a no-op returning the same `Match` reference. |
| E10 | Delete a mid-match event (e.g. the 12th of 80) | The event is removed, `sequence` re-densified, the whole match refolded. Every later event's score/serving/rotation is recomputed. A confirmation dialog states how many events are affected. |
| E11 | Deleting a mid-match event changes who won a finished set | Allowed. The refold recomputes `SetState.winner` from the stored `SetEndEvent` — but if the new score no longer satisfies `isSetWon`, the `set_end` is flagged inconsistent and the set is reopened (`status: 'live'`, `winner: null`) with a visible warning "Set riaperto: punteggio non più valido". |
| E12 | Timeout called after the set has ended but before the next `set_start` | Rejected: `DomainError('NO_LIVE_SET')`. The UI disables the timeout button between sets. |
| E13 | Timeout beyond `timeoutsPerSet` | Appended anyway; a non-blocking toast "Timeout oltre il limite" is shown (A5). |
| E14 | Substitution of a player who is not on court | Rejected: `DomainError('PLAYER_NOT_ON_COURT')`. The substitution dialog only lists the six on-court players as "out". |
| E15 | Substitution with `playerInId` already on court | Rejected: `DomainError('PLAYER_ALREADY_ON_COURT')`. |
| E16 | Substitution with `playerInId` marked `isAvailable: false` | Rejected: `DomainError('PLAYER_UNAVAILABLE')`; the player is not listed. |
| E17 | Libero selected as acting player | Always allowed (A4). If the libero is also in the lineup and rotates into P1 while we serve, a non-blocking warning appears; the serve is still recordable and counts in the statistics. |
| E18 | Duplicate shirt numbers in a roster (typed or imported) | The roster editor blocks saving with an inline error on both rows. On JSON import the match loads, the duplicates are flagged, and the archive screen shows "Numeri di maglia duplicati" — statistics are keyed on `Player.id`, never on the number, so nothing is miscounted. |
| E19 | An event references a `playerId` no longer in the roster | The event is kept and fully counted in team totals; in per-player tables it appears under a synthetic row "Giocatore sconosciuto" with the raw id in the tooltip. Deleting a player from the roster is therefore allowed but warned about ("N azioni già registrate"). |
| E20 | An event has a skill/outcome combination outside `ALLOWED_OUTCOMES` | Load succeeds; the event is marked `invalid` in the log with a warning icon. It still contributes to score (its terminality is outcome-driven and well defined) but is excluded from the per-skill statistics tables. |
| E21 | Stored `scoreAfter` disagrees with the recomputed fold (corrupt score sequence) | The fold is authoritative. On load, the mismatch is logged, the match is quarantined as a copy `<id>.corrupt-<ts>.json`, and the operator sees "Punteggio ricalcolato" with a before/after comparison; the repaired match is then saved. |
| E22 | `set_start` with fewer than six players, a duplicate id, or an unavailable player | Rejected before append: `DomainError('INVALID_LINEUP')`. The lineup screen cannot submit until L1/L2 hold. |
| E23 | A rally event arrives while no set is live (e.g. stale keyboard shortcut after set end) | Rejected: `DomainError('NO_LIVE_SET')`. Keyboard shortcuts are disabled whenever `snapshot.currentSet?.status !== 'live'`. |
| E24 | Both sides would satisfy `isSetWon` simultaneously (only reachable from corrupt data) | `evaluateSetEnd` evaluates `'us'` first, so `'us'` wins; the inconsistency is logged. Cannot occur from valid transitions since one point is added at a time. |
| E25 | `pointsToWinTieBreak` is larger than `pointsToWinSet`, or either is 1 | Accepted (A6 allows any 1..99). With target 1 and `winByTwo: true`, 1-0 is not a win — 2-0 is. Documented, not blocked. |
| E26 | The match is already won but the operator starts another set | `startSet` throws `DomainError('MATCH_ALREADY_WON')`. The UI offers "Chiudi partita" instead. |
| E27 | Two rapid clicks append the same action twice | Not prevented by the domain (each event has its own id). The action pad debounces at 250 ms and the log's undo makes the fix one click. |
| E28 | App crashes mid-rally, between the terminal event and the flush | The append and the flush are one operation for rally-terminating events (plan §8), so at most the last non-terminal quality event is lost. On restart the fold rebuilds everything from the surviving events. |
| E29 | A `note` is added between two sets | Allowed. Its `setIndex` is the index of the **last started** set and `atScore` is that set's final score. |
| E30 | Best-of-5 reaches 2-2 and the operator changes `bestOf` to 3 in settings mid-match | `MatchSettings` is frozen once `status === 'live'`; the settings form is read-only with the hint "Formato bloccato a partita iniziata". |

## 5. Worked example — 12-event trace

**Setup**: best-of-5, `pointsToWinSet: 25`, `winByTwo: true`, `startingServer: 'us'`.
Roster (shirt — short name): 1 Rossi, 2 Bianchi, 3 Verdi, 4 Neri, 5 Gialli, 6 Blu, 7 Mori.
Starting `Lineup` array (initial P1..P6): `[Rossi, Bianchi, Verdi, Neri, Gialli, Blu]`.

Reading the table: **Off** = `rotationOffset` after the event; **Server** = our P1 player when we
serve, `THEM` otherwise; positions come from `playerAtPosition(lineup, off, 'Pn')`.

| # | Event | Score after (us–them) | Point to | Serving after | Off | Server after | Court P1→P6 after |
|---|---|---|---|---|---|---|---|
| 1 | `set_start` lineup above, serving `us`, target 25 | 0–0 | — | us | 0 | Rossi | Rossi, Bianchi, Verdi, Neri, Gialli, Blu |
| 2 | `rally` Rossi · serve · point (ace) | 1–0 | us | us | 0 | Rossi | unchanged |
| 3 | `rally` Neri · attack · error | 1–1 | them | them | 0 | THEM | unchanged (they rotate, not modelled) |
| 4 | `rally` Gialli · reception · positive | 1–1 | null | them | 0 | THEM | unchanged (non-terminal) |
| 5 | `rally` Neri · attack · point (kill) | 2–1 | us | us | **1** | **Bianchi** | Bianchi, Verdi, Neri, Gialli, Blu, Rossi |
| 6 | `rally` Bianchi · serve · error | 2–2 | them | them | 1 | THEM | unchanged |
| 7 | `opponent_point` | 2–3 | them | them | 1 | THEM | unchanged (they were serving, no side-out) |
| 8 | `rally` Verdi · block · point | 3–3 | us | us | **2** | **Verdi** | Verdi, Neri, Gialli, Blu, Rossi, Bianchi |
| 9 | `timeout` them, atScore 3–3 | 3–3 | — | us | 2 | Verdi | unchanged |
| 10 | `rally` Verdi · serve · point (ace) | 4–3 | us | us | 2 | Verdi | unchanged |
| 11 | `substitution` Gialli → Mori (slot 4) | 4–3 | — | us | 2 | Verdi | Verdi, Neri, **Mori**, Blu, Rossi, Bianchi |
| 12 | `rally` Bianchi · attack · error | 4–4 | them | them | 2 | THEM | unchanged |

Key checks this trace pins down:

- Event 3: we lose a rally **while serving** → no rotation for us, serve passes to them.
- Event 4: a non-terminal quality event leaves score, serve and rotation untouched (A2) and carries
  `pointTo: null`, `scoreBefore === scoreAfter`.
- Event 5: side-out in our favour → `rotationOffset` 0→1 → the P2 starter (Bianchi) becomes the new
  P1 and therefore the server. The lineup **array** is unchanged.
- Event 7: `opponent_point` while they serve → no side-out, they keep serving, our offset is untouched.
- Event 11: the substitution rewrites lineup slot 4 (`Gialli`'s original P5 slot). With `off = 2`,
  slot 4 is currently displayed in position P3 — `(n + 2) % 6 === 4 → n = 2 → P3`. The offset is not
  touched, which is exactly why substitutions must edit the array in place.
- Undoing event 12 would restore 4–3, serving `us`, offset 2, server Verdi (§3.7).

## 6. Error type

```ts
export type DomainErrorCode =
  | 'NO_LIVE_SET'
  | 'SET_ALREADY_LIVE'
  | 'MATCH_CLOSED'
  | 'MATCH_ALREADY_WON'
  | 'INVALID_LINEUP'
  | 'INVALID_OUTCOME'
  | 'PLAYER_NOT_ON_COURT'
  | 'PLAYER_ALREADY_ON_COURT'
  | 'PLAYER_UNAVAILABLE'
  | 'PLAYER_NOT_IN_ROSTER'
  | 'EVENT_NOT_FOUND'
  | 'SETTINGS_LOCKED';

export class DomainError extends Error {
  constructor(readonly code: DomainErrorCode, message?: string) {
    super(message ?? code);
    this.name = 'DomainError';
  }
}
```

Every `DomainErrorCode` maps to one Italian message in `src/shared/copy/errors.ts`. Domain code never
contains Italian strings.
